# Code & Math Alignment: Experiment Engineering Manifesto

*How we write experiment code so that the code and the mathematics stay
on the same line — and the concrete engineering plan to back it.*

---

## 1. The Problem

The paper's algorithm block and the code should be the *same artifact*.
In practice they drift:

- The math *assumes* "the trie contains only utterable paths in $\mathcal{G}$."
  The code violated that (Freebase IDs) — caught by *measurement, weeks later*.
  It should have been an `assert`.
- The paper has 5 steps; `dca_v2_generate` buries them in a 200-line loop.
- The math is functional; `GraphConstrainedDecoding` holds hidden mutable
  state (`self.last_start_token`, `self.L_input`).
- Three conditions rebuild the same graph, oracle, DFS, and tokenization
  independently — 3× redundant work that no formula would describe.

Code and math "don't toe the same line" because code carries *state,
caching, and error-handling* that the math does not.  The goal is not to
eliminate those — it is to make them **explicit, named, and asserted**.

## 2. The Principle: Structural Isomorphism

> The code is a *transcription of the mathematical object*, not an
> implementation of a paragraph describing it.

| Math | Code |
|------|------|
| $\mathcal{T}(v) \cap \range(e) \neq \emptyset \Rightarrow$ admit | `def range_gate(relation, entity): return bool(types(entity) & range(relation))` |
| $\mathrm{admissible} = \text{range} \land \text{type}$ | `def is_admissible(...): return range_gate(...) and type_gate(...)` |
| $\text{trie} = \text{encode}(\{p : \text{admissible}(p)\})$ | `trie = build_trie(filter_paths(all_paths, is_admissible))` |
| "per-hop head pool" | `beam.head_pool: Set[str]` |

If the paper names it, the code names it.  No abstraction layer, no
renaming, no premature generalization.

## 3. The Five Practices

### 3.1 The paper's algorithm block and the code share structure.
Same step numbering, same names.  The paper's 5-step v2 loop becomes 5
functions: `enumerate_paths`, `apply_gates`, `build_trie`, `decode_hop`,
`advance_beam`.  Each is a pure function of its inputs.

### 3.2 Invariants are executable.
Every theorem in the paper gets an `assert` in the code:

```python
assert all(is_utterable(entity) for path in trie_paths for entity in path)
assert all(triple_in_graph(edge) for path in all_paths for edge in path)
assert filtered_paths ⊆ all_paths        # by construction
assert all_admissible(filtered_paths)     # gates pass on every kept path
```

When code and math diverge, the assert fires *that run*, not at defense.

### 3.3 Pure functions, no hidden state.
Each paper step = pure function of its inputs.  If state is needed
(cache, KV), it is *passed explicitly* or lives in a named cache object —
never mutated across calls inside a decoding callback.

### 3.4 One unit test per mathematical claim.
A 5-node toy KG, expected outputs computed *by hand from the math*, code
reproduces them.  We do not *trust* the code; we *prove* it against the
math on cases verifiable by inspection.

### 3.5 Visibility is a feature.
Per-phase timing, per-path counters, and a `--trace` mode that prints
exactly what the math says happens at each step.  `demo/step_by_step.py`
is the seed of this; it becomes the harness's trace mode so "Figure 3 in
the paper" and "terminal output" are the same artifact.

## 4. Engineering Plan (Ranked by Impact)

### P1 — Kill the 3× redundant precompute
`experiment.py` runs baseline, v1, v2 as three conditions.  Each
independently rebuilds the graph, runs DFS, builds the oracle, and
tokenizes every path.  **Fix:** a per-question `PrepCache` keyed by qid
holding `{graph, oracle, all_paths, path_strings, tokenized}` computed
once, reused across conditions.  Standard Python, pure win.

### P2 — KV-cache reuse across v2 hops
`dca_v2_generate` re-tokenizes the entire accumulated prompt every hop
and re-encodes it.  **Fix:** tokenize the base prompt once; pass
`past_key_values` of the shared prefix across hops, feeding only the
delta tokens to `generate`.  Turns $O(L^2)$ prompt compute into $O(L)$.
*Requires GPU validation* (trie matching in the callback must see
`<PATH>` in the visible delta, which it does — `<PATH>` is the last
token of the delta).

### P3 — No Freebase ID filtering (corrected from original plan)
Freebase IDs (`m.04kq1r9`) CAN be generated by the LLM — the baseline
predictions prove this (paths contain `m.04j60kh` etc.).  Filtering them
out of the trie destroys 11% of answer reachability (measured: 94%→89%).
**Data finding:** RoG-webqsp subgraphs have NO `type.object.name` triples,
so ID→name canonicalization is NOT possible from the subgraph alone.
**Fix applied:** removed `_is_freebase_id` filter from `_get_gated_paths`.
Gates run on ALL neighbors.  71% of paths go through Freebase IDs — the
old filter would have removed 90% of gated paths from a typical entity.

### P4 — Tokenize once, build all tries from the same token IDs
`build_unfiltered_trie`, `build_filtered_trie`, `build_trie_from_strings`
each call `tokenizer(path_strings)` independently.  **Fix:** a single
`build_trie_from_token_ids(tokenizer, token_ids)`; the three tries are
different views of one token table.

### P5 — Memory hygiene
Discard low-scoring beam outputs before materializing `res.sequences`.
Prefer sdpa/bf16 (already done).  Trie sizes (2,500 paths) are trivial
next to the 8B model; memory is not the bottleneck.

## 5. Honest Bounds

The model forward pass is 6+ of the 6.7 s/q.  P1–P4 save ~0.5 s/q and
fix correctness (the 11% reachability loss).  The runtime that actually
matters is $O(\text{model passes})$ — decided by search strategy (beam
width, hop count, KV reuse), **not** by trie size.  Path reduction that
does not reduce forward passes is a paper metric, not a latency win.
